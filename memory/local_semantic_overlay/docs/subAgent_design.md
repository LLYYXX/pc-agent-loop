# LSO 完整设计（多Agent版）

> 本文是 LSO（Local Semantic Overlay，本地语义覆盖层）的全文设计基准，历史设计收拢后的唯一精华归宿。
>
> **真值层级**：`ACCEPTANCE.md` 是最高契约（人定、冻结、只读），定义不可再降的根不变量（WHAT）。本文是它的完整解释与设计脉络，不替代它；若冲突，以 `ACCEPTANCE.md` 为准。
>
> **两类读者**：人——想知道"在建什么、为什么这么定、怎么权衡"，看这一份就够；Conductor——日常靠 prompt 里的 `TASK_CONSTRAINTS`（浓缩操作版）干活，遇边界情况回这里读全文。

---

## 0. 一句话

LSO 要建的是一台**「把用户任务里最该读懂的那一小块识别出来、覆盖好、并随使用持续校准」的机器**。

价值核心是**选对局部**，不是覆盖得多——覆盖对的 10% 比随机覆盖 50% 更够用。「局部」不是预算所限的残缺妥协，是一次主动的价值判断：把噪音、无关、次要的都筛掉，只把真正要紧的那块覆盖透。覆盖区**内**比盲搜更快、更准、更可复用、更可解释；覆盖区**外**老实回退底层搜索，不装懂。

产出形态是一条可导航链路：`tag → node → leaf → file`。让文件任务用"查链路"替代"猜关键词盲搜 ES"。

---

## 1. 责任分层（系统是什么）

整个系统是六层责任栈，每层负责什么、边界在哪都钉死：

| 层 | 负责 |
|----|------|
| **OS / 文件系统** | 真实文件的存在、读写、移动、删除、权限、恢复。 |
| **ES / Everything / 路径索引** | 全盘机械可见：路径、文件名、后缀、时间、大小、候选召回。 |
| **LSO 语义覆盖层** | 高价值文件的语义覆盖：tag、node、leaf、file binding、provenance、coverage state。 |
| **Agent 构建链路** | 语义判断与覆盖构建：筛选、压缩、打标、聚合、回写。本地代码先回到非 SubAgent 版本作为重构起点；角色边界和 proposal 契约仍按本文设计实现。 |
| **Core（约束与持久层）** | 结构化交接、校验、单写入、provenance、覆盖诚实、查询与维护。 |
| **Runtime Agent** | 接到任务后使用 LSO：任务语义 → tag 组合 → node → leaf → file。 |

关键的纵向分工：**创造价值的动作（选哪块、选什么算重要）在上层 Agent，通过 proposal 喂进来；Core 不做选择，只做承载。** 这是 Core 能极薄的根本原因——选择权不在它手里，它就不该有多少代码。ES 只返路径不做语义；Core 只持久化/校验/查询，不调 LLM、不自产语义。

### 1.1 为什么能这么分：系统层复用 GA 的 Agent 机制（重构的根）

上面那条"语义判断在上层 Agent"不是凭空假设了一个新组件，而是复用 GA 已有执行能力。当前本地实现会先回滚到非 SubAgent 版本，再按本文设计重构：在非 SubAgent 代码形态里保留调度、筛选、压缩、标记、聚合的职责边界和中间产物，把 proposal 交给 Core；Core 只校验、物化、保存、查询。

非 SubAgent 只是**实现起点**，不是降低约束：不能把角色边界糊回一个黑盒流程，不能把语义判断塞进 Core，不能把路径规则、业务分类、硬编码语义策略藏进配置 / SOP / prompt / 测试，也不能改 GA 主循环、工具 schema、`file_read`、memory injection、watcher、后台常驻进程或把 LSO 挂进 Agent loop。

具体复用这些 GA 能力：

- **GenericAgent 作为执行器**：LSO 构建任务本质上仍是普通 GA 任务，沿用现有系统提示、工具调用、文件读写、上下文管理和回合停止机制，不为 LSO 新造 agent runtime。
- **SOP / prompt / artifact 作为角色边界**：调度、筛选、压缩、标记、聚合先在非 SubAgent 实现中落成清晰阶段和中间产物；每段只产自己的结果，不越权直接改 overlay。这个边界必须能被审计 Agent 从 artifact 和源码里看见，不能只停留在自然语言自述。
- **Conductor / SubAgent 作为同构执行器替换**：以后若启用多 Agent，只是把同一套角色契约交给现有 `/subagent`、`/subagent/{id}`、`/chat` 控制面执行；artifact、proposal、Core 入口和审计口径不变。它不要求改 GA 主循环，不要求改 Core，不要求修改 Conductor 源码。
- **`agentmain.py --task` 作为文件化 worker 入口**：需要后台运行、复现或被监督时，复用现有 `temp/<task>/input.txt` → `output.txt` 任务形态。角色输入、artifact、自述和审计材料都落文件，方便审计 Agent 读取。
- **review / verify / supervisor 作为审查和看护能力**：review / verify 提供独立审计 Agent 的工作方式；supervisor 提供 `_keyinfo / _intervene / _stop` 看护长跑任务。它们只发现问题、要求返工或停止，不拥有写 overlay、改 Core 边界、宣布通过的权限。

职责落点因此很清楚：当前非 SubAgent 实现用普通 Agent / SOP 承载调度和角色阶段；未来多 Agent 实现只替换执行器，不替换契约。审计 Agent 管独立 verdict，Core 管 proposal 规约、物化、保存和查询。语义选择权卸载到 GA Agent 层，所以 Core 才能薄；写入权仍被收在 Core，所以这套机制仍是纯外挂、可摘除的。

> 术语澄清：本文出现的"复用"有两层，别混。**这里说的是架构层复用**——LSO 复用 GA 的 Agent 机制来承载语义角色。§2 / §3 里的"查询复用"是另一回事，指运行期沿已建好的链路命中、返回该读什么。

ES 只返路径不做语义；Core 只持久化/校验/查询，不调 LLM、不自产语义——这条边界正因为语义那一半被复用的 Agent 层接走了，才划得这么干净。

## 2. 核心链路（数据怎么流动）

```
发现候选 → 压缩结构 → 抽取 tag → 聚合 node → 形成覆盖 → 查询复用 → 缓存升降级 → 回写更新
```

- **发现候选**：ES/Everything 机械召回，砍掉噪音目录与无关文件，缩到可能要紧的范围。
- **压缩结构**：判断能否用目录/文件组承载语义，抬升信噪比。
- **抽取 tag**：给文件或 leaf 打可组合的 tag。
- **聚合 node**：把 tag 组织成可导航的 node。
- **形成覆盖**：链路落盘，带 provenance 与覆盖状态。
- **查询复用**：运行期沿链路命中，返回该读什么。
- **缓存升降级**：常命中的保温、久未命中的降冷——对"当前什么算最重要局部"的持续再排序（重要性随使用漂移）。
- **回写更新**：增量维护新鲜度与覆盖，作为新 proposal 重新进 Core。

这条链路整体就是一台"识别并维护最重要局部"的机器：前段（候选→tag）在选，中段（node→覆盖）在承载，后段（升降级→回写）在随用校准。

## 3. 职权划分（谁干什么）

| 角色 | 职责 |
|------|------|
| **调度者** | 决定下一步该谁干。 |
| **筛选者** | 找值得进入覆盖层的东西。 |
| **压缩者** | 判断能不能用目录 / 文件组承载语义。 |
| **标记者** | 给文件或 leaf 打可组合 tag。 |
| **聚合者** | 把 tag 组织成可导航 node。 |
| **规约层** | 检查格式、边界、证据。 |
| **持久层** | 保存覆盖结果。 |

前五个角色（调度/筛选/压缩/标记/聚合）是**语义判断**，在上层 Agent；后两个（规约/持久）是**机械承载**，在 Core。这条切线就是 §1 那条纵向分工的落地——价值判断在上、承载在下，互不越界。

## 4. 为什么这套划分是轻量且有效的

轻量与有效不是口号，要拿四样东西证明，它们是**证据，不是系统本身**：

- **轻量**：Core 规模低是"职责真被剥离干净"的证据，不是目标本身。当前约束是保持低假设容量、低内建知识、低语义权力、低侵入；core <1000 行只是代理指标，不是行数崇拜。短但过拟合的规则比稍长但通用的接口更坏。
- **解耦**：管线切成可单独关闭/替换的边界（搜索适配 / 证据管线 / 覆盖图构建 / 运行时导航 / 实验编排）。解耦让 Core 能薄（责任切开才推得动）、让 LSO 可摘除（拔掉后 GA 照常跑）、并且是消融的结构前提。
- **可插拔**：每段边界后端可换（ES/本地搜索可换、证据抽取可换），Core 只消费接口、不绑定实现。
- **可消融**：用 `--ablate` 单独关掉某能力，跑 A/B/C 对比、量化效果掉多少，从而证明"选对局部真创造了价值"并归因到具体组件。开关对应 `EvidenceFlags / OverlayFlags / NavigateFlags`（`no_dir_collection` `no_leaf_tags` `no_compression` `no_aggregation` `no_active_cold` `no_feedback` `no_semantic` `no_fallback` `path_only`），指标含 `search_calls / file_reads / overlay_writes / query_hits / fallback_hits / semantic_hits`。
  - **红线：可消融 ≠ 不计 Core 行数**。开关逻辑长在 Core 里、要计入行数，不能用"这块可消融"当借口把逻辑塞进开关后假装变薄。

消融把"选对的 10% 比随机的 50% 更够用"从一句信念，变成一个能被量化证伪的命题——关掉语义后命中率/读取数明显变差，才说明语义覆盖真在创造价值。

## 5. 根约束：十二条不变量（来自 ACCEPTANCE.md，最高契约）

> 不可再降的根。形式约束、语义有效性和真实收益统一交给审计 Agent、消融实验与人审闭环；代码层不承担最终裁决权。

1. **导航链是本体**——产品是 `tag→node→leaf→file`，其余信号是支撑。
2. **Core 只物化、不自产判断**——语义分类/打标签来自上层 proposal，Core 不自行读原始文件生成语义。
3. **可摘除**——拿掉 LSO，GA 主循环照常工作；Core 只能是旁路索引。
4. **轻量性检验器**——Core 保持低假设容量、低语义权力、低侵入；core <1000 行只是代理指标。禁用压格式、搬运逻辑、塞文档 / prompt / 配置规避规模约束。
5. **单写入入口**——主索引落盘只经唯一函数；绕过/新增/间接落盘都算 drift。
6. **多源信号分立、可溯、不伪 semantic**——命中可多通道，每条带 channel provenance；标 `semantic` 必须由真实语义链路支撑，不能用文件名/路径串匹配冒充。
7. **覆盖不自欺**——采样结论不得冒充完整覆盖；`sampled` 与 `full_coverage` 不能同真；要能表达覆盖边界与采样状态（"区外老实回退"的契约化）。
8. **持续更新是维护，不是重规划**——增量维护新鲜度/覆盖/热冷，不重造分类体系；重新筛选/打标/聚合必须作为新 proposal 重新进 Core。
9. **可归因（C vs D）**——能区分收益来自已建链路（C）还是多智能体建造编排（D）。
10. **真有用**——真实文件任务走运行期路径，比盲搜更稳、可复用、可解释。
11. **审核与判定分离，判官独立**——"审核"不等于"判定通过"；最终通过由独立审计 Agent 给出 verdict，再由人审确认。audit 须基于 proposal、provenance、artifact、源码差异、运行记录和本契约，不只看自然语言总结。
12. **commit 锁死**——git commit 仅在人审确认 audit pass 后由人执行；Conductor / SubAgent / master 无手工 commit、无"有条件合入"权力；未通过的 proposal 不进主索引但可进 log。

## 6. 验证：审计、消融、真实任务，各管一段

| 验证 | 性质 | 管什么 |
|------|------|--------|
| **独立审计 Agent** | 对抗性、证据化、可复核 | 是否违反十二条不变量；是否存在搬运、伪语义、越权写入、覆盖自欺、自评替代审查 |
| **消融** | 实证、定量、可重复 | 哪个能力真创造价值、价值归谁（#9/#10 的硬证据，研究期跑，不给日常 Agent） |
| **真实任务 triage** | 非确定、抽样、烧 token | 真实 case 上像不像那么回事，是否比盲搜更稳、更可解释 |

独立审计 Agent 必须逐条给出 `PASS|FAIL|UNCERTAIN + 证据`。证据来源包括：proposal、artifact、run log、overlay 快照、源码差异、真实查询结果、消融结果和本文契约。master / Conductor 只能整理材料、发起审计、汇总 verdict，不能替审计 Agent 下通过结论。

审计重点：

1. Core 是否只物化 proposal，没有从原始文件自产语义。
2. 写入是否仍只有唯一入口，未通过 proposal 是否只进 log 不进主索引。
3. tag / node / leaf 是否有证据支撑，`supporting_leaf_ids` 是否是真实锚点。
4. 采样状态、覆盖边界、fallback 是否诚实表达。
5. 多 Agent 建造收益是否和运行期导航收益分开归因。
6. SOP / prompt / 配置是否承载了 case-specific 路径规则、业务分类或硬编码语义策略。
7. 真实任务是否显示 LSO 链路确实减少盲搜、减少无关读取、提升解释性。

## 7. 路径：怎么走到达标，以及之后

**当前路线**：本地代码先回到非 SubAgent 版本，然后按本文角色设计重构。非 SubAgent 是代码形态，不是目标降级；重构仍必须保留筛选、压缩、标记、聚合、规约、持久的边界和 artifact / proposal 交接。

**主线**：

1. **以回滚后的非 SubAgent 版本为重构起点**：恢复简单本地形态，去掉临时编排假设。
2. **按角色设计重构，而不是退回黑盒流程**：发现筛选、内聚压缩、语义打标、节点聚合、规约、持久分别有清楚输入输出。
3. **保持纯外挂边界**：不改 GA 主循环、不改工具 schema、不改 `file_read`、不做 memory injection、不加 watcher / 常驻后台进程、不把 LSO 挂进 Agent loop。
4. **保持 Core proposal-only**：Core 只做规约、物化、保存、查询；语义判断只来自上层 proposal。
5. **用真实任务和消融证明价值**：比较盲搜、搜索适配、LSO 链路命中的读取数、命中质量、解释性和复用性。
6. **由审计 Agent 做独立审查**：每个重要 checkpoint 由审计 Agent 按 §6 审查 proposal、artifact、源码差异和运行记录；master / Conductor 只汇总 verdict。
7. **人审后固化 baseline**：只有人审确认 audit pass 后，才由人 commit。

**角色与权限**：

- **普通 Agent**（当前代码形态）：按 SOP 执行 LSO 构建与运行期使用，产 proposal、artifact、bounded report。
- **Conductor**（可替换调度层）：只在多 Agent 执行器路线启用，负责派工、收报告、要求返工和向用户汇总；无裁决权、无 commit 权、无直接写 overlay 权。
- **SubAgent**（可替换角色执行者）：只负责被分派的筛选 / 压缩 / 标记 / 聚合子任务，输出 artifact，不直接写主索引。
- **审计 Agent**：独立读材料、跑必要复核、出 verdict；不接受被审对象自评替代。
- **人**：唯一 commit 门控；最终审。
